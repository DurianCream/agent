# Submit the Common Result

Use runtime/agentctl.py at the repository root. Ordinary conversation does not require an execution record.

1. Start with `python runtime/agentctl.py init --module <registered-id> --task <task-id> --objective <objective> --criterion <acceptance-criterion>`. Repeat --criterion as needed. For a registered target repository, add --repo <repo-id> and all four scope flags: --project <project-id> --service <service-id> --environment <environment-id> --issue <issue-id>. New repository-bound tasks require the complete scope. Do not guess an environment or copy the latest task scope. To continue existing work, inspect task.json instead of creating a replacement task.
2. Run `transition <task-id> running`. Store actual artifacts in outputs/<task-id>/ and verification logs in runs/<task-id>/evidence/.
3. Populate the fixed fields in runs/<task-id>/result.json. artifacts.path and verification.evidence are repository-root-relative. artifacts.sha256 may be null initially; submit computes it. Write user-facing narrative in Korean; schema keys remain unchanged.
4. Link real verification IDs in acceptance_criteria.verification_ids. Passed/failed checks require readable evidence files. Record unexecuted checks as not_run, and non-applicable checks as not_applicable with a reason. Never mark completed without proving every required criterion.
5. Run `validate <task-id>` and then `submit <task-id>`. Generate result.md from result.json; do not manually edit the report. Record post-submission changes under a new task ID. Repository-bound submission also refreshes the durable work record; checkpoint meaningful progress before handoff or interruption.
6. For a repository with enabled .agent-work/automation.json, automatically run `python runtime/repoctl.py finish --task <task-id>` after a completed submission. The main agent must already have captured the baseline and registered its exact task-owned paths with begin/track. Saving a report alone is not completion of the publication workflow. Preserve and report any commit/push failure; never force-push or include unrelated changes. A user request to skip publication overrides this default.
7. Generate the complete seven-section Korean result.md from result.json: basic information; objective and acceptance criteria; result summary; work performed; artifacts; verification results; unresolved issues and next actions. Final chat may instead briefly state the result, verification, limitations, and next action in Korean; it need not repeat all seven sections. State when an item is not applicable, unverified, or unexecuted. Concise chat never replaces the durable record or required lifecycle.

For light actual changes, write concise content in the existing required fields and link relevant task evidence; retain the same init/validate/submit/checkpoint/finish path and applicable mandatory gates. The optional ordinary-prose-v1 runtime profile is available only to new capability-enrolled tasks with exact paths already allowlisted in committed .agent-work/submission-profiles.json. It supports existing nonexecutable UTF-8 docs/prose/*.txt ordinary wording edits only; root README/AGENTS, instructions, policies, configurations, code, new/deleted files, mixed changes and unresolved uncertainty remain full. Filename extension or author tier alone never establishes eligibility. Do not delete result.json fields, invent a bypass, or replace the generated report with an informal note. Any change to profile eligibility or gates uses the full high-risk path and an explicit compatibility proposal.

For every change, preserve the objective, tier and one-line reason, actual changed files/behavior and decisions, checks/results/evidence and not_run reasons, independent review verdict/stable findings/repair status, and unfinished work/next actions. Update at meaningful completion, review handoff, and repair completion, rather than every tool invocation. High-risk work also records environment, permissions, versions, and recovery conditions. Use existing work, verification, limitations, next_actions, and linked evidence; do not add unversioned result fields or duplicate empty documents. Completion requires satisfied required criteria/checks, no unresolved required defect, and current durable records.

Apply these revised instructions to new tasks by default. In-progress tasks retain their acceptance criteria and frozen contracts; never auto-migrate them or let this procedure change waive its own pre-change controls.

Schema and policy sources are shared/schemas/result.schema.json and shared/policies/common.json. Existing tasks use their frozen versions under runs/<task-id>/snapshot/files/. Structural checks do not establish the truth of evidence.

Keep the task scope immutable. Preserve legacy unclassified records without inferring a classification. An active legacy binding can receive its first explicit scope with repoctl set-scope; submitted reports and snapshots must not be rewritten.

## Optional runtime profile commands

The default remains the enrollment's original full suites. Do not edit enrollment, selection state, baseline, proof or seal JSON by hand. Preserve all result fields and record tier/reason, actual files, checks, findings and remaining actions in the existing result and linked evidence.

1. After tracking exact owned files and freezing the candidate, obtain `python runtime/control_gate.py candidate --task <task-id>`. An independent evaluator examines the actual diff and uncertainty, then supplies a task-owned input JSON with `candidate_digest`, `reviewer` (`subject`, `session`, both different from the enrolled author), `reason`, `evidence` paths and an `impact` map for every exact owned path. Each impact contains `ordinary_prose: true`, `no_behavior_change: true`, `uncertainty: "none"` and a concrete `rationale`. These are local declarations, not authenticated identities or semantic proof.
2. Register this approval using `python runtime/control_gate.py select-profile --task <task-id> --input runs/<task-id>/evidence/profile-input.json`. The runtime rechecks committed opt-in policy, exact candidate, existing document bounds and unchanged protected dependencies. Failed eligibility does not silently select light.
3. Execute `python runtime/control_gate.py run-tests --task <task-id> --suite light-document-integrity`. The fixed checker records three actual structural/integrity checks. It does not replace semantic review or claim full regression coverage.
4. Bind the executed checks and final result through the existing independent `assess` command. Reuse the same substantive review when its candidate/evidence remain current; a second complete audit is not required. Continue checkpoint/validate/submit/finish normally. Any new selection record invalidates earlier profile-specific test/review proofs even for identical candidate bytes.
5. For increased impact, stale selection, or profile-configuration maintenance, use `python runtime/control_gate.py promote-full --task <task-id> --reason "<concrete reason>"`. Promotion is irreversible through the CLI and requires the originally enrolled full suites plus current independent review. It never rewrites snapshots or prior selections. Full maintenance may modify the companion profile configuration; light may not.

The profile's scope is intentionally narrower than the conversational light tier. The checked-in activation includes one descriptive example, docs/prose/project-overview.txt. Future allowlist changes require full review/publication and affect fresh enrollment only. Local cooperating checks cannot prevent coordinated same-user record tampering, direct Git bypass or impersonation. Host permissions and standing publication destination checks remain authoritative.

## Compact committed task evidence

For tasks whose immutable publication baseline contains `.agent-work/evidence-policy.json`, commit only `spec.md`, `record.json`, `report.ko.md` and `evidence/summary.json` under `.agent-work/tasks/<id>/`. Store original logs, exhaustive searches, test ledgers and review details in `runs/<id>/evidence/`; do not copy them into committed records. Keep result narratives concise as they are repeated in generated records.

The summary contains only a `checks` list (1..64). Each check has `id`, `result` (`passed`, `failed`, `not_run`, `not_applicable`), `command` (at most 1024 characters), numeric `metrics` (at most 16), and `evidence` (1..32 objects containing only the task-local `runs/<id>/evidence/` path and lowercase SHA-256). Put explanations and detailed outcomes in raw evidence. Unknown fields and raw payloads are rejected. Preserve one identical summary in `runs/<id>/evidence/summary.json`, have the independent evaluator include it in review evidence, and track only its committed copy. Freeze referenced originals before hashing; never reference the summary itself. Review binding remains required; publication verifies original hashes through the summary, without committing originals.

The publication limit is 65,536 bytes (64 KiB) per committed task file and 262,144 bytes (256 KiB) for all four task files. A 64 KiB summary comfortably accommodates tens of short check outcomes and hashes while stopping full audit dumps. The total is deliberately four times the file cap: it makes the overall budget explicit and prevents growth if the allowed file count changes. These are repository storage budgets, not evidence-retention limits. Validation names unexpected, missing or oversized files and runs before commit and again against real committed bytes before push.

Activation comes only from the policy in the task's original committed `publication.base_head`; an uncommitted policy cannot activate or disable it. Preserve historical records, snapshots and existing task contracts unchanged. This policy-changing task follows its original gates and uses a reviewed summary copy wherever possible. A follow-up change can revert source/configuration through normal review and publication; it must not rewrite existing baseline contracts or historical evidence.
