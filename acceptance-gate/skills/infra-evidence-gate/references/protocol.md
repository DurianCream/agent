# 실행 기록 계약과 검사기의 한계

## 실행 환경과 책임

이 프로토타입은 Python 3 표준 라이브러리와 Linux/WSL의 `O_NOFOLLOW`, `O_DIRECTORY` 파일 열기 기능을 사용한다. 추가 설치와 네트워크 접근은 필요 없다. 조율자는 별도 `RUN_DIR`에 아래 네 UTF-8 JSON 파일을 준비하고, 각 역할은 결과를 조율자에게 전달한다. 최종 증거 검사 역할과 검사기는 입력을 수정하지 않는다.

각 JSON 문서는 객체여야 한다. 필수 필드와 아래 형식을 검사하며, 추가 메타데이터는 허용하지만 명령 문자열을 실행하지 않는다. JSON 키 중복, `NaN`·무한대, 8 MiB를 넘는 입력 JSON은 거부한다. ID는 비어 있지 않은 문자열이며 목록·항목 집합 안에서 중복을 허용하지 않는다. 대소문자를 포함한 ID의 정확한 문자열로 참조한다.

## 요청: `request.json`

```json
{
  "goal": "실제 요청 목표",
  "criteria": [{"id": "criterion-1", "description": "확인할 완료 기준"}],
  "required_checks": ["check-1"]
}
```

`goal`과 기준의 `description`은 비어 있지 않아야 한다. `criteria`는 최소 1개이다. `required_checks`는 필요한 검사 ID 목록이며 설명·문서 작업처럼 실행 검사가 필요 없으면 빈 배열을 사용할 수 있다. 작업에 맞는 기준을 조율자가 정하며 증거가 없다는 이유로 이미 요구된 기준·검사를 제거하지 않는다.

## 계획: `plan.json`

```json
{
  "tasks": [{"id": "task-1", "description": "실제 작업", "depends_on": []}],
  "criteria_ids": ["criterion-1"],
  "required_checks": ["check-1"]
}
```

`tasks`는 최소 1개이다. `depends_on`은 같은 계획에 존재하는 선행 작업 ID 목록이다. 없는 의존성과 순환 의존성은 오류이다. `criteria_ids`와 `required_checks`의 집합은 요청과 정확히 일치해야 한다. 순서의 차이는 허용한다.

## 작업: `work.json`

아래는 형식 설명용 예시이다. `evidence/result.txt`는 실제로 작성해야 하는 상대경로이고 `<실제 파일의 SHA256>`은 해당 파일 내용의 SHA-256 해시로 바꿔야 한다. SHA-256은 파일 바이트에서 계산하는 64자리 16진수 요약값이다. 자리표시자가 남아 있으면 검사에 통과하지 않는다.

```json
{
  "status": "COMPLETE",
  "summary": "실제 수행 결과",
  "evidence": [{"id": "evidence-1", "path": "evidence/result.txt", "sha256": "<실제 파일의 SHA256>"}],
  "checks": [{"id": "check-1", "status": "PASS", "exit_code": 0, "evidence_ids": ["evidence-1"]}],
  "criteria": [{"id": "criterion-1", "status": "VERIFIED", "evidence_ids": ["evidence-1"], "explanation": "이 증거가 기준을 확인하는 이유"}]
}
```

- 작업 `status`: `COMPLETE`, `BLOCKED`, `FAILED` 중 하나.
- 검사 `status`: `PASS`, `FAIL`, `NOT_RUN` 중 하나. `exit_code`는 실제 정수 또는 `null`이며 `false`는 정수 0으로 인정하지 않는다.
- 기준 `status`: `VERIFIED`, `UNVERIFIED`, `FAILED` 중 하나. `summary`와 `explanation`은 문자열이다.
- `evidence_ids`는 등록한 증거 ID 목록이다. 없는 증거 ID를 참조하면 오류이다. 기준과 기록한 검사에는 하나 이상의 존재하고 해시가 맞는 증거가 필요하다.
- 요청 기준의 평가와 필수 검사의 기록이 빠지면 증거 부족이다. 요청에 없는 기준 평가 ID는 오류이다. 추가 검사는 허용하되 기록한 모든 검사의 실패·미실행·종료 코드와 증거도 검사한다.

증거 경로는 `RUN_DIR` 안의 `/`로 구분한 상대경로이어야 한다. 절대경로, Windows 드라이브 경로, 역슬래시, 빈 경로 요소, `.`·`..` 요소, 심볼릭 링크는 거부한다. 내부 대상을 가리키는 링크도 거부하며 실행 디렉터리 경로의 링크와 입력 문서의 링크도 허용하지 않는다. 증거는 일반 파일이어야 하며 디렉터리·파이프 등 특수 파일은 거부한다.

## 비평: `critique.json`

```json
{
  "verdict": "PASS",
  "summary": "현재 작업과 증거를 확인한 비평 결과",
  "work_sha256": "<비평한 work.json의 SHA256>",
  "findings": [{"blocking": false, "description": "작업을 막지 않는 참고 사항"}]
}
```

`verdict`는 `PASS`, `REWORK`, `NEEDS_EVIDENCE` 중 하나이다. `findings`는 없으면 빈 배열이며 각 `blocking`은 실제 불리언, `description`은 비어 있지 않은 문자열이다. `work_sha256`은 비평 담당이 확인한 `work.json`의 실제 바이트에서 계산한다. 검수 이후 내용을 바꾸면 비평을 다시 해야 하며 조율자가 해시만 갱신하여 검수를 대체하면 안 된다.

## 실행과 판정

```bash
python3 "<스킬 경로>/scripts/check_evidence.py" "<RUN_DIR>"
```

실제 경로로 자리표시자를 바꾼 뒤 Linux/WSL 셸에서 실행한다. 현재 작업 디렉터리는 자유이며, 절대경로를 사용하면 경로 혼동을 줄일 수 있다. 검사기는 네 JSON과 기록된 증거만 읽고, 하위 명령·네트워크·파일 쓰기를 수행하지 않는다.

표준 출력은 `verdict`, 한국어 `reasons` 배열, 읽은 입력 문서의 `input_sha256` 객체를 가진 JSON이다. `input_sha256`은 증거 파일 목록이 아니라 네 입력 문서의 해시이다. 이유에 원시 입력 값이나 로그 내용을 복사하지 않는다.

| 판정 | 종료 코드 | 의미 |
|---|---:|---|
| `PASS` | 0 | 작업 완료, 모든 기준 확인과 증거 일치, 필수 검사 통과와 정수 종료 코드 0, 비평 통과와 차단 지적 없음, 비평 대상 작업 해시 일치 |
| `REWORK` | 1 | 형식·참조·계획 오류, 명시적 실패, 허용되지 않은 경로, 변경된 증거 또는 오래된 비평 |
| `NEEDS_EVIDENCE` | 2 | 필요한 기록·증거 누락, 미실행·미확인·차단 또는 파일 접근 불가 |

여러 문제가 함께 있으면 `REWORK`가 `NEEDS_EVIDENCE`보다 우선한다. 파일 읽기 도중 변경이 관찰되면 재작업으로 판정한다. 잘못된 셸 호출은 Python·인자 처리 오류로 종료할 수 있으므로 JSON 출력과 종료 코드가 모두 정상적으로 반환되었는지도 확인한다.

## 독립 검토가 필요한 한계

해시 일치는 기록 이후 파일 바이트가 같다는 뜻이다. 로그의 진위, 테스트의 적절성, 요구사항 충족, 실제 시스템 상태를 증명하지 않는다. 검사기는 증거 내용을 의미적으로 해석하거나 검사 명령을 다시 실행하지 않으므로 조작한 기록도 형식과 해시가 맞으면 구조 검사를 통과할 수 있다. 최종 담당이 실제 산출물과 증거 내용을 독립적으로 검토해야 한다.

이 검사는 파일별 읽기 시점의 상태를 확인하며 전체 디렉터리를 잠그거나 원자적 스냅샷을 만들지 않는다. 검사 후 산출물 변경은 자동으로 감지되지 않으므로 작업을 고정한 뒤 검사하고, 이후 관련 내용이 바뀌면 재비평·재검사한다. 운영 적용 권한이나 복구 성공을 이 판정에서 추론하지 않는다.
