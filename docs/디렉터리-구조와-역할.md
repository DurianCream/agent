# multi 디렉터리 구조와 역할

`multi`는 역할별 에이전트 지침, 공통 정책·계약, 실행 도구, 작업 기록을 분리한 저장소입니다. `core/`와 `modules/`는 **누가 무엇을 판단하고 수행하는지**, `runtime/`은 **그 절차를 코드로 어떻게 실행·검사하는지**를 담습니다.

테스트 환경은 시험 목적에 맞춰 필요한 시점에 OS와 정확한 버전을 정하고, 사용자가 해당 VM 또는 ISO를 제공하는 방식으로 준비합니다. 특정 OS 버전을 모든 작업의 고정 전제로 삼지 않습니다.

## 현재 구조

```text
multi/
├─ AGENTS.md                 작업·위임·기록·게시 규칙
├─ registry.json             활성 역할과 역할 파일 위치
├─ README.md                 사용자 시작 안내
├─ core/                     공통 관리 역할 5개
├─ modules/                  전문 수행 역할 3개
├─ shared/
│  ├─ policies/              공통 규칙과 관찰 정책
│  ├─ schemas/               결과·모듈·제어 데이터 계약
│  ├─ skills/                재사용 작업 절차의 원본
│  └─ knowledge/             공통 지식 자료
├─ runtime/
│  ├─ tests/                 실행 도구의 회귀·실패 사례 시험
│  └─ *.py, *.json, *.toml   작업·검증·게시·설정 도구
├─ evals/                    평가 기준과 검토 자료
├─ docs/                     한국어 사용·운영 안내
├─ .codex/                   Codex용 생성 설정과 역할 프로필
├─ .agents/skills/           원본 스킬을 찾아 읽도록 하는 생성 어댑터
├─ .agent-work/              Git에 보존하는 작업 명세·보고·선별 증거
├─ runs/                     로컬 실행 상태·스냅샷·시험 및 평가 기록
├─ outputs/                  로컬 사용자 산출물과 생성 결과 보고서
├─ work/                     임시 실험·도우미·복구 체크아웃
├─ .venv-controls/           제어 도구용 Python 의존성 환경
└─ .git/                     Git 객체·브랜치·원격 설정 등 내부 자료
```

`__pycache__/` 같은 캐시는 실행 과정에서 생성되며 기능이나 역할을 정의하는 원본이 아닙니다. `work/` 아래에 복구용 저장소 사본이 있어도 현재 프레임워크의 원본은 이 문서가 속한 `multi` 루트입니다.

## 8개 에이전트 역할

역할 선택의 기준은 `registry.json`이며, 각 역할의 `module.json`이 버전·범위·참조 스킬을, `instructions.md`가 수행 절차를 정의합니다.

| 위치·역할 | 주된 책임 | 다른 역할과의 구분 |
|---|---|---|
| `core/orchestrator/` | 요청 범위와 완료 기준을 정하고 전문 담당을 배정하며 결과를 통합 | 직접 권한을 만들어 주는 승인 서비스가 아님 |
| `core/policy-manager/` | 거버넌스 담당: 정책 적용, 권한 범위, 위험·예외·미확정 조건 판단 | `proceed/revise/escalate` 의견을 제시하며 실행 권한을 발급하지 않음 |
| `core/evaluator/` | 작성자와 분리된 검증 담당: 결과·시험·증거·회귀·위험을 독립 검토 | `accepted/rework/inconclusive`를 판정하며 자기 구현을 자기 승인하지 않음 |
| `core/skill-manager/` | 역할·공통 스킬·등록 정보·버전과 호환성 관리 | 제품 기능 구현보다 에이전트 작업 체계의 유지에 집중 |
| `core/knowledge-manager/` | 출처·설계 결정·프로젝트 지식과 기록 정리 | 추측을 사실로 바꾸거나 다른 작업의 문맥을 임의로 섞지 않음 |
| `modules/coding/` | 코드 구현·수정·디버깅·시험 | 보통 변경 작성자이며 최종 독립 검토는 evaluator가 담당 |
| `modules/infrastructure/` | 인프라·배포·실행 환경·운영 구성과 적용 검증 | 계획 성공과 실제 배포 성공을 구분 |
| `modules/oss-rnd/` | 오픈소스 소스 분석·재현 실험·비교·도입 판단 | 출처와 고정 리비전, 사실·가설을 구분 |

이 폴더들에 지침이 있다는 사실만으로 에이전트 프로세스가 계속 실행되거나 운영체제 권한이 분리되지는 않습니다. 실제 에이전트 실행과 도구 권한은 호스트가 제공합니다.

## runtime의 역할

| 파일·그룹 | 현재 역할 |
|---|---|
| `agentctl.py` | 작업 생성, 역할·정책·계약 스냅샷, 상태 전이, 결과 검증·제출 및 보고서 생성 |
| `repoctl.py` | 저장소·작업 범위 연결, 체크포인트, 저장 기록 조회·복구 |
| `repo_automation.py` | 작업 소유 파일 추적, 정확한 원격·브랜치·기준 커밋 검사, 커밋·푸시와 원격 확인 |
| `control_gate.py` | 게시 검사 신규 작업 등록, 시험·독립 검토·산출물 연결, 제출 봉인과 실제 커밋 게시 검사 |
| `sync_codex.py` | 역할·스킬 원본으로부터 Codex 설정과 발견용 어댑터를 생성·대조 |
| `codex-settings.toml`, `context-hooks.json`, `context_checkpoint.py` | 프로젝트 설정의 원본과 컨텍스트 기록 훅 처리 |
| `legacy_memory.py` | 과거 작업의 분류·가져오기와 범위가 확인된 기록의 취급 |

따라서 거버넌스 에이전트와 검증 에이전트는 `core/`에 있고, 그 판단을 기록·대조하거나 제출·게시를 차단하는 결정적 코드는 `runtime/`에 있습니다.

게시 검사는 로컬 CLI의 제출·게시 경로를 검사합니다. 통과만으로 직접 Git 사용, 다른 도구 경로, 자격증명 접근까지 차단됐다고 볼 수 없습니다.

## 설정 원본과 생성 파일

`core/`, `modules/`, `shared/skills/`의 원본을 수정한 뒤 `runtime/sync_codex.py`로 `.codex/agents/`, `.codex/config.toml`, `.agents/skills/`를 동기화합니다. 생성 파일만 수정하면 원본과 어긋나거나 다음 동기화에서 충돌할 수 있습니다.

`runtime/native-map.json`은 생성 파일의 일치 여부를 추적합니다. `runtime/repos.local.json`과 `.codex/hooks.json`은 이 컴퓨터의 경로·실행 연결을 담는 로컬 자료이므로 Git에 게시하지 않습니다. 역할 선언과 생성 설정이 호스트의 실제 권한 제한을 바꾸는 것은 아닙니다.

## 작업 기록은 어디에 남는가

| 위치 | 보존하는 내용 | Git 취급 |
|---|---|---|
| `.agent-work/tasks/<task-id>/` | 작업 명세, 한국어 보고서, 검토한 증거 사본과 해시 | 작업 소유 파일로 명시해 게시 |
| `.agent-work/index.json`, `INDEX.md` | `record.json`에서 생성하는 로컬 작업 목록 | Git 추적 제외 (`python runtime/repoctl.py index --repo multi`) |
| `.agent-work/automation.json` | 승인된 게시 원격·브랜치 | 버전 관리 |
| `.agent-work/gates.json` | 신규 작업의 게시 검사 선정 범위·필수 시험·검사 정책 | 버전 관리; 등록된 작업에서는 고정 |
| `runs/<task-id>/` | 실행 상태, 시작 당시 스냅샷, 원본 시험 로그, 평가와 게시 영수증 | 기본적으로 로컬 전용 |
| `outputs/<task-id>/` | 사용자 산출물과 `result.json`에서 생성한 `result.md` | 기본적으로 로컬 전용 |
| `work/` | 실험 파일, 임시 스크립트, 복구용 체크아웃 | 로컬 전용 |

`result.json`이 결과의 원본이며 `result.md`를 직접 고치지 않습니다. 모든 실행 로그를 Git에 올리는 방식이 아니라, 검토한 명세·보고서·필요한 증거 사본을 `.agent-work/`에 남깁니다. 과거 제출 결과와 시작 당시 스냅샷은 새 작업에서 덮어쓰지 않습니다.

## 요청별 테스트 환경

구체적인 시험 목적과 필요한 기능을 먼저 정한 뒤, 해당 시험에 맞는 환경을 요청합니다. 사용자는 그때 기존 VM 또는 설치 ISO를 제공할 수 있습니다. 아직 특정 시험의 환경 요구가 정해지지 않았다면 즉시 VM이나 ISO를 준비할 필요는 없습니다. Ubuntu 24.04 같은 특정 버전은 모든 테스트의 기본 조건이 아닙니다.

환경 요청에는 다음 내용을 포함합니다.

| 구분 | 확인할 내용 |
|---|---|
| 시험 목적 | 무엇을 검증하며 어떤 결과를 통과·실패로 판단하는지 |
| 운영체제 | OS·배포판 이름, 에디션, 정확한 버전·빌드, CPU 아키텍처 |
| 자원·가상 하드웨어 | 필요한 vCPU·메모리·디스크, 가상 하드웨어 기능과 호스트 지원 여부 |
| 부팅·보안 기능 | UEFI/BIOS, Secure Boot, TPM 등 해당 시험에 필요한 기능과 설정 |
| 네트워크·자격증명 경계 | 관리 접속, 허용할 통신 대상·방향, 계정 권한, 접근 금지 저장소·비밀과 보호할 게시 경로 |
| ISO 제공 시 | 이미지 출처, 배포자가 제공한 검증 자료와 SHA256, 이미지에 해당하는 OS·버전 정보 |
| 기존 VM 제공 시 | 정확한 VM 식별자와 접속 대상, 실제 실행 중인 OS·버전을 확인한 증거. VM 이름이나 ISO 파일명만으로 추정하지 않음 |

이미지 해시 일치는 실행 중인 OS 버전이나 호스트 격리까지 증명하지 않습니다. 접속·설치 후 실제 버전과 필요한 기능을 다시 확인합니다. 비밀번호·개인키·토큰은 환경 요청이나 채팅에 포함하지 않습니다.

로컬 Hyper-V는 ISO로 테스트 VM을 준비할 때 사용할 수 있는 경로 중 하나입니다. 현재 세션의 Hyper-V 관리 호출은 권한 부족으로 거부됐으므로, 이 경로를 선택하면 관리자가 준비 절차를 실행해야 합니다. 기존 VM을 제공받는 경우에는 그 VM의 실제 상태와 접근 경계를 별도로 확인합니다.
