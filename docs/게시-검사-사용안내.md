# 게시 검사

게시 검사는 현재 `agentctl`의 완료 제출과 `repoctl finish`의 게시 경로에서 검사를 강제합니다.

## 적용 대상

`.agent-work/gates.json`에 선정된 `multi / agent-framework / development`의 새 작업부터 등록합니다. 이슈는 각 작업의 정확한 범위를 사용합니다. 등록 전에 시작된 작업과 과거 제출 기록은 기존 방식으로 유지합니다.

작업 등록 당시의 범위·기준 커밋·설정과 정책을 고정합니다. 등록된 작업의 제어 파일을 삭제하거나 설정을 낮추어 완료하는 방식은 허용하지 않습니다. 로컬 등록 기록 자체를 수정할 수 있는 사용자까지 막는 보안 경계는 아닙니다.

## 작업 순서

1. 범위를 지정해 `agentctl init`합니다. 이 명령 하나로 게시 기준 기록, 게시 검사 등록, 작업 시작(running)까지 끝납니다. 작업 소유 파일은 `repoctl track --path <파일>`로 등록하거나, `repoctl track --changed`로 후보 목록을 확인한 뒤 `--yes`를 붙여 등록합니다. 다른 열린 작업이 소유한 파일은 거부됩니다.
2. 구현·사용자 산출물·작업 명세를 정리한 뒤 `python runtime/control_gate.py candidate --task <작업ID>`로 검사 대상을 확인합니다. 최종 `result.json`과 거기에 참조하는 시험·검토 근거도 평가 등록 전에 확정해야 합니다.
3. `python runtime/control_gate.py run-tests --task <작업ID> --suite <설정된-suite-ID>`로 선택된 시험을 모두 실행합니다. 명령·실행 결과·로그와 실행 전후 파일 내용을 기록합니다. 판정은 로그 글자가 아니라 시험 실행기가 따로 남긴 결과 수치로 합니다. 실패·오류가 있거나 skip·expected failure·unexpected success가 하나라도 있으면 실패이고, 실행된 시험이 0개여도 실패입니다.
4. 작성자가 아닌 evaluator가 실제 파일과 시험 증거를 검토하고, 결과에 참조된 검토 보고서를 완성합니다. evaluator가 직접 평가 입력을 작성하고 `python runtime/control_gate.py assess --task <작업ID> --input <저장소-상대경로>`로 기록합니다. 평가의 `evidence`에는 최종 산출물과 보존할 검토 근거를 포함합니다. 평가 등록 뒤에는 결과나 근거 파일을 수정하지 않습니다. 평가 결과는 `finish`가 게시되는 `record.json`에 자동으로 첨부하므로 결과에 다시 적지 않습니다.
5. `repoctl finish --task <작업ID>`를 실행합니다. `finish`가 제출, 커밋 생성과 검증, 푸시까지 처리합니다. 미리 확인하려면 `python runtime/control_gate.py status --task <작업ID>`와 `agentctl validate`를 쓸 수 있습니다.

평가 입력에는 `kind`, `candidate_digest`, `reviewer`의 `subject`·`session`, `verdict`, 현재 작업의 검토 근거 파일 경로 배열인 `evidence`가 필요합니다. `kind`는 완료이고 소유 제품 파일이 있으면 `product`, 그 외(제품 없는 완료, partial·failed·cancelled 종료)는 `records`이며, 게시 종류와 다르면 거부됩니다. verdict는 `accepted`, `rework`, `inconclusive` 중 하나입니다. 평가자 이름은 선언된 구분값이며 인증된 신원은 아닙니다.

## 차단과 재검증

필수 시험이나 독립 검토 누락, 시험 실패, 검토 이후 파일·증거·정책 변경, 작업 범위 불일치는 완료 제출을 차단합니다. 수정 후에는 변경된 내용을 대상으로 필요한 시험과 검토를 다시 수행합니다. 기존 증거의 해시나 판정을 고쳐서 통과시키지 않습니다.

거버넌스의 `proceed`만으로 검토한 파일·정책·증거의 일치를 확인하는 게시 검사를 충족하지 않습니다.

게시 검사는 제출한 대상과 실제 생성된 커밋, 변경 경로, 부모 커밋, 승인된 원격·브랜치를 대조합니다. `finish`는 커밋 객체를 먼저 만들어 검증하고, 통과한 뒤에야 작업 상태·브랜치·색인을 바꾸고 푸시합니다. 검증에서 실패하면 작업 상태·작업 트리·색인·브랜치는 그대로이므로 원인을 고치고 `finish`를 다시 실행합니다. 중간에 끊기거나 푸시가 실패해도 같은 `finish`를 다시 실행하면 저장된 단계부터 같은 커밋으로 이어 갑니다. 다른 작업이 잠금을 잡고 있다고 나오면 실행 중인 `finish`가 없는지 확인한 뒤 `repoctl unlock --task <작업ID>`를 씁니다. 이 명령은 주인 프로세스가 끝난 잠금만 지웁니다. 강제 푸시나 별도 완료 커밋 생성으로 우회하지 않습니다.

## 범위와 한계

현재 로컬 CLI를 따르는 작업에 대한 검사입니다. 에이전트 지침, 로컬 시험 실행 기록, 파일 해시는 서명된 신뢰 증명이나 규제 준수 인증이 아닙니다. 작성자와 평가자는 동일 운영체제 사용자 권한으로 파일에 접근할 수 있습니다. 직접 Git 사용·구버전 CLI·로컬 검사 코드나 등록 원장 전체 변경을 막으려면 호스트 격리와 보호된 게시 서비스 또는 원격 서버 검사가 추가로 필요합니다.

새 clone에서는 `python -m venv --copies .venv-controls`로 게시 검사 시험용 환경을 준비합니다. Windows에서는 `.venv-controls/Scripts/python.exe`, Linux에서는 `.venv-controls/bin/python`을 사용합니다. 현재 게시 검사 시험은 Python 표준 라이브러리를 사용하며 기존 환경의 설치 패키지를 제거할 필요는 없습니다. 필수 시험 환경이 없거나 실행할 수 없으면 검사 실패로 표시하며 자동으로 의존성을 다운로드하거나 통과로 처리하지 않습니다.

등록된 작업은 시작 당시 `gates.json`을 고정하므로 작업 중 검사 설정을 변경할 수 없습니다. 같은 선정 범위의 새 작업도 기존 설정을 고정하므로, 새 작업을 만드는 것만으로 설정 변경이 가능해지지는 않습니다. 향후 설정 변경에는 별도 마이그레이션 절차가 필요하며 이 버전은 그 절차를 제공하지 않습니다. 현재 작업의 등록을 삭제하거나 검사를 끄는 방법으로 우회하지 않습니다.

## 변경 영향에 따른 시험 선택

이 기능이 게시된 **이후 시작한 작업**만 기준 커밋의 `.agent-work/impact-tests.json`을 등록에 고정합니다. 기존 작업의 등록·스냅샷·필수 전체 게시 검사 시험은 바뀌지 않습니다. `gates.json` 자체의 변경 금지는 유지합니다.

`python runtime/control_gate.py select-tests --task <작업ID>`로 실제 필수 suite와 경로별 선택 이유·digest를 확인합니다. 기존 문서·모듈 지침·스킬·지식·eval·생성 어댑터는 `impact-document-integrity`(sync_codex 확인, doctor, 결과 계약, UTF-8/충돌 표식 검사)를 선택합니다. 개별 runtime 모듈은 대응표의 명시된 테스트를 선택하며 섞인 범위는 합집합입니다. 대응표 범위 안의 새 파일은 해당 suite를 선택합니다. 삭제·모드 변경·실행 파일이나 `runtime/tests`의 새 파일·미등록 경로·소유권 밖 dependency 변경·대응표 변경은 필수 게이트 시험과 대응표의 모든 suite를 실행합니다. gates, 결과 스키마, 비밀값 검사 설정과 공용 runtime 경로(보호 경로)는 필수 게이트 시험에 해당 경로의 대응표 시험을 더합니다. AGENTS.md와 workflows는 문서 suite와 독립 검토로 확인합니다.

evaluator는 기존 평가 필드에 `impact_digest`와 모든 소유 경로의 검토 근거 문자열을 담은 `impact_review` 객체를 추가합니다. 선택 결과는 시험 증거에 저장되고 평가·제출 시 다시 대조합니다. 매 릴리스 직전에는 `runtime/tests` 전체를 직접 실행해 대응표 누락을 점검합니다.

## 미완료 작업 닫기와 이어받기

미완료 작업은 후속 작업 없이 자기 기록을 직접 게시해 닫습니다.

1. `result.json`에 상태(`partial` 또는 `failed`)와 한계를 적습니다. 취소라면 취소 사유를 적습니다.
2. 독립 evaluator가 `kind`가 `records`인 평가를 기록합니다. 미완료 작업은 시험을 실행하지 않습니다.
3. `repoctl.py finish --task <작업ID> --close partial|failed|cancelled`를 실행합니다. `partial`·`failed`는 결과 상태와 같아야 하고, `cancelled`는 아직 제출하지 않은 작업을 끝냅니다.

기록 게시는 작업 기록 파일(spec, record, report, 증거 요약)만 커밋합니다. 미완료 제품 파일은 작업 트리에 그대로 남고 게시되지 않으며, 제품 파일과 실행 dependency의 일치도 검사하지 않습니다. 원격 브랜치가 앞서 있어도 그 사이 이 작업의 기록 폴더가 바뀌지 않았으면 원격 끝에 이어서 게시합니다. 이때 로컬 브랜치와 색인은 건드리지 않으며, `finish`가 로컬 브랜치가 원격보다 뒤에 있다고 알려 줍니다. 원격이 기준 커밋에서 갈라졌거나 기록 폴더가 바뀌었으면 거부합니다.

제품 파일이 없는 완료 작업도 `records` 평가 뒤 `--close` 없이 `finish`로 기록을 게시합니다. 이 경우 선택된 시험은 실행해야 하며, 소유 제품이 없고 바뀐 dependency가 없으면 선택된 시험이 없을 수 있습니다.

제품 파일을 이어받으려면 원작업을 `--close partial`로 닫은 뒤, 정확히 같은 네 범위의 새 작업에서 다음을 실행합니다.

- `repoctl.py transfer-ownership --task <후속ID> --source-task <원ID> --path <정확한파일>`: partial 제출 때 보존된 후보와 현재 파일의 Git 표현·모드·원시 해시가 모두 일치할 때만 소유권을 받습니다. 원작업이 기록을 게시하기 전이든 후든 가능하고, 같은 파일은 한 번만 이관됩니다. 후보 증거가 없는 과거 작업은 추측으로 이전할 수 없습니다. 이후 수정은 후속 작업의 시험·독립 평가·봉인 대상으로 처리합니다. 후속 작업은 원작업의 기록을 게시하지 않습니다.

partial 후보의 파일 봉인은 시험 환경이 없어도 가능하며, 제품 파일이 없는 partial과 cancelled 종료는 이전 가능한 후보를 만들지 않습니다. 원작업의 로컬 `runs/`가 필요하며, 기록만 있는 새 clone에서 원작업 상태를 추측하지 않습니다.

예전 버전의 게시 검사로 등록된 작업은 등록 기록이 온전하면 `--close`로 기록만 닫을 수 있고, 제품 게시는 새 작업으로 시작해야 합니다. 등록 기록이 빠졌거나 서로 어긋나면 지금처럼 거부합니다.

## 게시 직전 비밀값 검사

일반 게시와 기록 게시 모두 브랜치를 움직이기 전에 만들어 둔 실제 커밋을 검사합니다. 재시도에서도 같은 커밋을 다시 검사합니다. 대상은 게시되는 변경 파일의 전체 내용이며 생성된 작업 기록도 포함합니다. 무관한 작업 파일과 과거 전체 이력은 검사하지 않습니다.

현재는 외부 실행 파일 없이 동작하는 최소 정규식 검사로 개인키 시작 블록, AWS·Google 키 형식, Azure 연결 키, 비밀번호·토큰 할당과 시험용 canary를 차단합니다. 따옴표 안의 비어 있지 않은 값은 앞 공백·공백만 있는 값도 차단하며, 빈 할당과 따옴표 없는 꺾쇠 자리표시는 통과합니다. 탐지하면 푸시하지 않고 파일 경로와 줄 번호만 표시합니다. 검사 자체가 불가능하면 차단하며 위치를 특정할 수 없는 파일 오류는 줄 번호 0입니다. 비밀값이나 일치한 본문은 보고서에 남기지 않습니다.

오탐 예외는 `.agent-work/secret-scan-allowlist.json`의 `paths` 배열에 저장소 상대 파일 경로를 정확히 등록하는 방법 하나뿐입니다. 와일드카드·디렉터리·인라인 예외는 지원하지 않습니다. 허용 목록 변경도 작업 소유 파일로 등록하여 검수·게시해야 적용되며, 작업 트리만 고쳐서는 이미 준비된 커밋의 검사를 우회할 수 없습니다. 허용 파일은 전체 내용이 검사 제외되므로 최소한으로 사용합니다.

검사에 걸리면 브랜치·색인·작업 상태는 바뀌지 않습니다. 값을 제거하고 기존 검증·검수를 갱신한 뒤 `finish`를 다시 실행합니다.

이 검사는 포괄적인 비밀 탐지기가 아닙니다. 사용자 정의 형식·압축 내부·암호화 데이터는 보장하지 않습니다. UTF-8 및 BOM이 있는 UTF-16/32를 처리하며, 모호한 NUL 포함 데이터·손상된 Unicode·16 MiB 초과 파일은 검사 불가로 차단합니다. 단일 파일 허용 목록으로 명시적으로 검토한 예외만 처리할 수 있습니다.
