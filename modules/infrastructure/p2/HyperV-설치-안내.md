# 실제 테스트 시점의 OS·VM 준비

**OS나 버전을 미리 고정하지 않습니다.** 에이전트가 실제 테스트에 필요한 OS·버전·요구 기능을 먼저 알려주면, 사용자가 해당 환경의 기존 VM 또는 새 VM용 ISO를 제공합니다. OS와 무관한 설계·코드·모의 검증을 진행하기 위해 지금 VM이나 ISO를 준비할 필요는 없습니다.

현재 PC에는 Hyper-V가 실행 중이지만 이 세션에는 관리자·Hyper-V Administrators 권한이 없습니다. 준비 코드가 있어도 VM 생성·게스트 설치·P2 보안 적용이 완료된 것은 아닙니다. 실제 생성이 필요한 경우에만 관리자 실행을 요청합니다. 기능 재설치·재부팅·광범위한 관리 그룹 가입은 자동으로 요구하지 않습니다.

## 에이전트가 테스트 전에 확인할 내용

- 테스트 목적과 정확한 작업 범위
- 필요한 OS 이름, 버전·빌드·에디션, 아키텍처
- UEFI/Secure Boot 템플릿, vTPM 등 필요한 기능
- 해당 테스트와 OS에 필요한 CPU·RAM·디스크 및 접속 방식
- 기존 VM 사용인지, 제공된 ISO로 새 VM을 만들 것인지

OS별 요구 사항은 실제 대상이 결정된 뒤 확인합니다. 이름이나 ISO 파일명만 보고 운영체제를 추정하지 않습니다. 다른 버전·부팅 방식으로 임의 대체하거나 보안 기능을 꺼서 통과시키지 않습니다.

## 기존 VM을 제공하는 경우

VM ID·이름, OS·버전, IP 또는 접속 별칭, 허용할 계정·인증 방식, 공개 호스트 키 또는 인증서 지문을 알려주세요. 비밀번호·개인키 본문·토큰은 보내지 않습니다.

에이전트는 연결 대상의 신원을 확인하고 게스트가 보고하는 실제 OS·버전을 **읽기 전용으로 검증한 뒤** 테스트를 선택합니다. 이름이 같다는 이유로 기존 VM을 생성 스크립트에서 재사용·변경·재설치하지 않습니다. SSH를 쓴다면 공개 호스트 키 지문을 확인하며 `StrictHostKeyChecking=no`로 우회하지 않습니다. 다른 원격 프로토콜이면 그 방식에 맞는 서버 신원을 검증합니다.

## ISO로 새 VM을 준비하는 경우

준비 API 0.2.0은 OS 이름·정확한 버전·아키텍처·부팅 템플릿·자원을 모두 명시적으로 받습니다. ISO의 출처와 제조사가 제공한 서명·해시를 먼저 확인해야 합니다. 로컬 파일에서 계산한 해시를 그대로 기대값으로 쓰면 출처 검증이 되지 않습니다. ISO 해시 일치는 바이트의 일치만 보여주며, 선언한 OS나 실제 설치 버전의 증명이 아닙니다.

프로필을 로드하지 않는 **새 64비트 관리자 PowerShell(`-NoProfile`)**에서 검토된 스크립트·모듈을 사용합니다. 기존 스위치는 **Hyper-V 관리자 → 가상 스위치 관리자**에서 선택합니다. 준비 스크립트는 Windows 시스템 경로의 Hyper-V 모듈만 불러오며 새 스위치·NAT·방화벽 규칙을 만들지 않습니다.

아래는 **형식 안내용 자리표시자이며 선택된 OS나 실행할 기본값이 아닙니다.** 실제 요청이 결정된 뒤 값을 채웁니다.

```powershell
$request = @{
    VmName = '<multi-p2-로 시작하는 이번 테스트의 고유한 소문자 이름>'
    OsName = '<요청한 OS 이름>'
    OsVersion = '<정확한 버전 또는 빌드>'
    Architecture = 'amd64' # 현재 도구의 지원 범위
    SecureBootTemplate = '<MicrosoftWindows 또는 MicrosoftUEFICertificateAuthority>'
    CpuCount = <요청한 정수>
    MemoryGiB = <요청한 정수>
    DiskGiB = <요청한 정수>
    IsoPath = '<실제 로컬 ISO 절대 경로>'
    IsoSha256 = '<신뢰할 수 있는 출처에서 확인한 64자리 SHA256>'
    SwitchName = '<선택한 기존 스위치 이름>'
    VmPath = '<신뢰된 로컬 상위 경로 아래, 끝 폴더 이름이 VmName과 같은 새 경로>'
}
.\modules\infrastructure\p2\New-P2VM.ps1 @request -WhatIf
```

`-WhatIf`로 확인한 뒤 같은 요청에서 `-WhatIf`만 빼면 새 VM을 **정지 상태**로 생성합니다. 설치 화면까지 시작하려면 `-Start`를 명시합니다. 이미 정지 VM을 만들었다면 생성 스크립트를 재실행하지 말고, 관리자가 출력된 VM ID를 확인해 시작합니다.

VM 이름은 `multi-p2-` 뒤에 소문자 영숫자·하이픈 1~40자를 사용하고 접미사 시작·끝은 영숫자여야 합니다. 같은 이름의 VM이나 저장 경로가 있으면 재사용·삭제하지 않고 중단합니다. 경로 끝 이름은 요청 VM 이름과 같아야 합니다. ISO와 저장 위치는 실제 로컬 고정 드라이브여야 하며 네트워크 매핑·SUBST·PowerShell 별칭·재분석 지점을 거부합니다. 저장소의 기존 상위 경로는 관리자/System 통제 하에 있어야 합니다. 검사를 통과시키려고 드라이브 루트나 기존 시스템 폴더의 ACL을 변경하지 마세요.

현재 범위는 **Gen2·AMD64·Secure Boot On**입니다. vTPM·레거시 BIOS/Gen1·ARM 구성은 제공하지 않습니다. 필요한 테스트에는 이미 해당 기능이 올바르게 설정된 VM을 요청하거나 별도 구현·검증해야 합니다. TPM이 필요한 대상에 이 도구가 TPM을 자동 제공한다고 가정하지 않습니다. OS 이름을 적었다고 그 OS의 호환성이 검증된 것은 아닙니다. 선택한 Secure Boot 상태·템플릿은 구성 조회 결과와 일치해야 시작할 수 있습니다.

자원 범위는 CPU 1~64개(호스트 논리 CPU 이내), RAM 1~128 GiB(물리 RAM에 2 GiB 여유 필요), 동적 디스크 8~256 GiB입니다. 디스크에는 요청 용량·ISO 사본·2 GiB 여유가 필요합니다. `-Start`는 가용 RAM이 **요청 RAM + 2 GiB 이상인지** 시작 직전에도 확인합니다. 이 수치는 도구의 제한이며 OS별 최소 요구 사항이나 실제 부팅 성공의 증명이 아닙니다. 다른 앱·VM을 종료해 자원을 확보하지 않습니다.

## 설치 후와 실패 시

출력의 `requested_guest`는 요청값이며 `installed_guest`·`guest_compatibility`는 `unverified`입니다. 실제 게스트 신원·OS·버전 탐지와 worker·검증기·publisher 분리 및 직접 Git/HTTP 차단 시험이 끝나야 해당 테스트와 P2 적용 결과를 판정할 수 있습니다.

오류가 나면 새 VM이나 저장소 일부가 남을 수 있습니다. 생성 명령이 실패했다고 VM이 없다고 단정하지 않습니다. 관리자는 요청 VM 이름·실제 ID·승인 경로를 확인해야 합니다. 자동 삭제·기존 VM 재사용·강제 재부팅은 하지 않습니다. 기존 데스크톱 Codex의 호스트 도구·연결 서비스 권한도 VM 생성만으로 제한되지 않습니다.
