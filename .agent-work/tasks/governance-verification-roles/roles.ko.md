# 거버넌스 담당과 검증 담당의 역할 및 실행 책임

## 1. 기본 정보

기존 `policy-manager`를 거버넌스 담당으로 구체화하고, `evaluator`는 독립적인 결과 검증을 맡도록 정의한다. 새 에이전트 종류는 추가하지 않는다. 기존 AX 실행 통제 설계의 역할 부분을 보완하는 작업이다.

- 작업: `governance-verification-roles`
- 범위: `multi / agent-framework / development / governance-verification-role-definition`
- 선행 설계: `ax-controls-design`, 커밋 `68c978bce5454825563674de148326b31797e3e3`
- 변경 대상: 두 역할의 지침·모듈 설명과 오케스트레이터의 인계 절차, 생성되는 에이전트 설정
- 유지 대상: 기존 8개 역할 ID, 현재 권한, 결과 계약 1.0.0, 과거 작업 기록과 스냅샷

역할 지침은 에이전트의 작업 방식을 정한다. 실행 권한과 승인 검사를 코드로 강제하는 기능은 선행 설계의 후속 구현 범위다.

## 2. 목표 및 완료 기준

각 담당자가 무엇을 판단하고 어떤 근거를 남겨야 하는지 명확히 하며, 에이전트의 권고·사람의 승인·runtime 검사 결과가 섞이지 않도록 한다.

| 주체 | 담당 질문 | 결과의 성격 |
|---|---|---|
| 거버넌스 담당 | 이 업무에 어떤 정책·위험·조건이 적용되는가? | 정책·위험 검토와 조치 권고 |
| 검증 담당 | 이 결과와 증거가 요구사항을 실제로 충족하는가? | 기준별 검증 평가와 결함 보고 |
| runtime | 정해진 필수 조건이 충족됐는가? | 코드로 확인 가능한 검사·차단 |
| 사람·호스트 | 누가 어떤 권한을 부여하고 잔여 위험을 책임지는가? | 권한 부여·예외·위험 수용과 실제 접근 제한 |

정책 역할의 긍정적인 권고나 검증 역할의 수용 판정만으로 운영 실행 권한이 생기지 않는다.

## 3. 결과 요약

### 거버넌스 담당 policy-manager

**판단할 내용**은 업무 목적과 범위, 적용 정책의 의미, 데이터 민감도, 대상 환경, 영향 범위, 예외·충돌·불확실성이다. 이미 존재하는 승인이 해당 작업까지 포함하는지도 근거와 함께 검토한다.

**남길 산출물**은 검토한 작업·정책·변경 버전, 적용 조건과 근거, 위험 설명, 필요한 통제·검증 항목, 미확인 요구사항과 책임자, 다음 중 하나의 권고다.

- `proceed`: 현재 조건에서 계속 진행하도록 권고한다. 필요한 실행 승인과 host 검사까지 통과했다는 뜻은 아니다.
- `revise`: 계획이나 통제 조건을 수정해야 한다.
- `escalate`: 권한·예외·위험 수용 등 책임 있는 담당자의 판단이 필요하다.

**맡지 않는 권한**은 자기 승인, 운영 자격증명 발급, 호스트 제한 해제, 규정 준수 인증, 무단 정책 활성화다. 정책 변경안은 근거와 검증 조건을 갖춰 제안하고, 실제 활성화는 기존 권한과 승인 절차를 따른다.

정책·대상 환경·민감 데이터·권한 범위가 변하거나 해석이 필요한 경우에 호출한다. 기존 허가와 정책이 명확한 단순 조회·되돌릴 수 있는 개발 작업마다 별도 거버넌스 호출을 추가하지 않는다.

### 검증 담당 evaluator

**판단할 내용**은 요구사항 충족, 결과의 정확성·완전성, 증거의 관련성, 테스트의 적절성, 실패·경계 조건, 회귀 위험과 불확실성이다. 작성자의 완료 선언보다 실제 파일·실행 결과·검토 대상 버전을 우선한다.

**남길 산출물**은 기준별 결과와 근거, 실제 실행한 검사와 하지 않은 검사, 수정할 결함과 심각도, 검토 대상 버전, 다음 중 하나의 평가다.

- `accepted`: 검토 범위의 필수 기준이 충분한 증거로 충족된다.
- `rework`: 실제 결함이나 기준 미충족이 있어 수정해야 한다.
- `inconclusive`: 증거 부족·오래된 결과·범위 불명확 등으로 판단할 수 없다.

기준별 결과는 `passed`, `failed`, `not_run`, `not_applicable`로 구분한다. 역할의 평가 값은 공통 결과 보고서의 `completed` 같은 작업 상태와 다른 값이다.

**맡지 않는 권한**은 자신이 작성한 결과의 독립 승인, 통과를 위한 기대 결과 변경, 실행하지 않은 테스트의 증거 생성, 정책·권한 우회, 배포 승인과 규정 준수 인증이다. 필요한 수정은 작성자에게 돌려보내고 변경된 부분을 재검토한다.

### runtime과 나눌 경계

| 업무 | 에이전트가 판단할 부분 | 현재 코드의 검사 | 후속 구현에서 강제할 부분 |
|---|---|---|---|
| 작업 범위 | 요청의 대상·목적이 무엇인지 해석 | 저장소·프로젝트·서비스·환경·이슈별 기록 선택과 일치 검사 | 실행 대상과 인증된 작업 범위의 일치 |
| 정책 적용 | 규칙의 의미·충돌·예외와 위험 조건 | 일반 정책·버전·스키마 구조 확인 | 신뢰된 활성 정책 선택과 허용 목록 검사 |
| 승인 | 기존 승인 범위와 추가 판단 필요성 검토 | 호스트의 권한·승인 규칙이 별도로 적용 | 요청 내용·대상·정책에 묶인 승인 검증, 만료·재사용 차단 |
| 결과 품질 | 실제 요구사항·실패 사례·근거의 타당성 | 결과 형식, 필수 기준과 검증 항목의 연결 | 신뢰된 테스트 실행 증거 및 검토 대상 버전 연결 |
| 증거 신뢰 | 관찰한 내용이 결론을 뒷받침하는지 판단 | 파일 존재·크기·해시 검사 | 작성자와 분리된 검사기·기대 결과·평가자 신원의 확인 |
| 게시 | 조건 충족 여부와 남은 위험 설명 | 정확한 원격·브랜치·소유 파일·기준 커밋·게시 결과 검사 | 직접 Git·이전 CLI 우회를 막는 별도 게시 경계 |
| 사고·복구 | 영향·원인·안전한 복구안·재개 조건 평가 | 현재 범용 실행 중단기는 없음 | 새 실행 차단, 진행 중 상태 확인, 권한 있는 재개 |

후속 강제 기능은 아직 구현되지 않았다. 같은 권한의 CLI나 에이전트 지침만으로 우회 불가능한 통제를 만들 수 없으며, 호스트·실행 계정·자격증명·네트워크·게시 서비스의 경계가 필요하다.

## 4. 수행 내용

### 두 담당자의 인계와 충돌 처리

1. 오케스트레이터가 작업 범위, 완료 기준, 대상 버전, 기존 승인과 미확인 사항을 정리한다.
2. 정책·위험 해석이 필요한 작업은 거버넌스 담당이 적용 조건과 검증 요구를 제시한다.
3. 전문 에이전트가 계획·산출물·테스트 근거를 만든다. 보호된 실행에는 실제 권한과 구현된 통제가 별도로 적용된다.
4. 작성하지 않은 검증 담당이 결과와 근거를 독립적으로 평가한다.
5. 결함은 작성자에게 반환한다. 정책과 검증의 결론이 충돌하면 요구사항·증거·책임자를 확인하며 다수결로 해결하지 않는다.
6. 중요한 미확인 사항이 있으면 해당 변경·게시만 보류한다. 이미 허용된 비민감 조회·진단 등 독립 작업은 계속할 수 있다.
7. 대상·정책·권한·중요 산출물·증거가 바뀌면 영향을 받는 판단을 다시 받는다.

### 예시: 운영 방화벽 변경

거버넌스 담당은 대상 서비스와 운영 환경, 기존 승인 범위, 영향받는 연결, 금지된 변경, 복구와 추가 승인 조건을 정리한다. 인프라 담당은 정확한 변경안과 검증 계획을 만든다. 검증 담당은 연결 영향과 복구 가능성을 입증하는 증거를 확인하고 잘못된 가정·누락을 지적한다.

미래의 실행기는 승인된 대상·변경 내용·사전 상태가 정확히 일치하는지 확인한 뒤 허용된 동작만 수행하고, 실행 후 상태를 읽어 확인한다. 현재 작업은 역할 지침을 정하는 것이므로 운영 방화벽을 변경하거나 해당 실행기를 설치하지 않는다.

### 예시: 승인된 개발 작업의 Git 게시

기존 상시 승인이 지정한 저장소·브랜치와 현재 작업 소유 파일의 범위에 들어가면 불필요한 재승인을 요구하지 않는다. 검증 담당은 결과와 필요한 증거를 검토하고, 현재 게시 코드는 목적지·소유권·커밋·원격 결과를 검사한다. 다른 목적지나 더 넓은 권한은 기존 승인의 확장으로 간주하지 않는다.

## 6. 검증 결과

실제 검증 결과는 생성되는 `result.json`과 `result.md`에 기록한다. 모듈 등록·버전·생성 설정·계약 호환성 검사와 독립 내용 검토를 구분한다. 검토 사례는 기대 동작을 정의하며, 사례를 작성했다는 사실을 실제 운영 동작 시험 통과로 보고하지 않는다.

역할은 계속 `experimental` 상태로 유지한다. 실제 장기 업무에서의 판단 품질, 격리된 실행기의 강제력, 공격 저항성은 후속 구현·행동 평가 대상이다.

## 7. 미해결 사항 및 다음 조치

현재 적용되는 변경은 역할 지침과 인계 절차다. 역할별 권고 형식은 일반 작업 결과와 구분해서 사용하며 공통 결과 계약 1.0.0을 변경하지 않는다.

후속 P0 구현에서는 이 책임 분리를 정책 판정기·계약 검증기에 연결한다. P1에서는 신뢰된 검증 증거와 제출 검사를 연결하고, 보호된 실행·게시의 우회 방지는 P2의 실제 격리와 함께 검증한다. P2 시범 운영부터 신뢰할 수 있는 최소 감사 기록을 남기며, 실행 전 필수 감사 기록을 저장할 수 없으면 실행을 막는다. P3에서는 이를 바탕으로 운영 감시·평가 보정과 관리 범위를 확대한다.

고위험 운영 전에 업무 책임자·승인자·정책 관리자·사고 대응자·데이터 보존 책임자를 실명 또는 조직의 인증된 ID로 지정해야 한다. AI 역할 이름만으로 이 책임이 배정됐다고 간주하지 않는다.
