# oss-rnd 역할 행동 평가

가상 사례 R01–R04를 각각 새로운 `oss-rnd` 피평가 에이전트에서 한 번씩 실행했습니다. 독립 판정은 **의미상 대응 4건 통과, 입력 예산 4건 실패, 출력 예산 4건 통과**입니다. 따라서 계약상 **종합 통과 0건·실패 4건**입니다. 실패를 숨기거나 통과하도록 지침·예산을 바꾸지 않았습니다.

## 계약과 변경 범위

기존 `evals/harness-behavior-v1.json`은 동결된 계약이므로 원본 바이트와 기존 13개 사례 값을 그대로 보존했습니다. 그 옆의 `evals/harness-behavior-v2.json`은 **R01–R04만 담은 보충 계약**이며 v1을 대체하거나 마이그레이션하지 않습니다. 관리 지침과 사례 필드 형식은 동일합니다. 각 사례의 한도는 입력 **16,000 UTF-8 바이트**, 출력 **800 UTF-8 바이트**, 응답 **1라운드**입니다. 기존 사례는 재실행하지 않았습니다.

제품 변경은 새 계약과 `evals/results/oss-rnd-behavior-20261111.json` 두 파일뿐입니다. 역할 지침·스킬·하네스 코드·기존 시험 코드는 수정하지 않았고, 실제 지식 색인에 가상 결정을 넣지 않았습니다.

## 입력 제공과 계측의 한계

필수 `owner-led-delivery.md`만 17,381바이트로 이미 사례 한도 16,000바이트를 넘었습니다. 필수 자료를 빼거나 한도를 늘려 통과시키지 않고, 초과를 사전 기록한 채 각 사례를 한 번 실행하여 의미상 대응을 관찰했습니다.

입력은 보존된 관리자 안내문, 실제 전달 접두문 119바이트, 실제 도구 반환 텍스트를 합산했습니다. 파일 원문 크기는 사전 정보이며 도구 반환에 더해 이중 합산하지 않았습니다. 네이티브 기록에서 관리자 안내문은 암호화돼 있어 보존된 평문과 실제 전달 평문이 같은지를 독립적으로 복구·대조할 수 없습니다. 그래서 표의 합계는 **재구성 값**으로 표시했습니다. 반면 독립적으로 관찰한 접두문과 도구 반환만의 하한도 모두 16,000바이트를 초과하므로 입력 예산 실패 판정은 이 한계에 의존하지 않습니다.

R01·R02는 내부 명령의 출력 허용량을 높였지만 외부 도구 래퍼의 기본 출력 제한으로 필수 자료 일부가 잘렸습니다. 사례 질문은 전달됐으나 전체 필수 지침을 읽은 뒤의 행동을 입증하지는 못합니다. 이 두 사례는 재실행하지 않았습니다. R03·R04는 아직 실행하기 전에 외부 출력 허용량을 명시하는 관리 안내만 보완했고, 기존 사전 기록과 변경된 안내의 바이트 수·해시를 모두 보존했습니다. 사례·평가 기준·입력 자료 자체는 바꾸지 않았으며, 후반 두 사례의 전체 자료 전달은 독립 검수로 확인했습니다. 따라서 네 사례가 완전히 같은 전달 조건이었다고 주장하지 않습니다.

고정 계약에 따라 호스트가 넣은 지침·환경 정보는 제외했습니다. 식별 가능한 네이티브 사용자 블록은 사례별 3,476바이트이며, 나머지 시스템·개발자 프롬프트 전체 크기는 알 수 없습니다. 숨은 추론·총 토큰·과금은 측정하지 않았습니다. 출력 한도는 모든 가시적 중간 설명과 최종 답변 텍스트에 적용했습니다. 도구 인수 바이트는 별도로 R01 349, R02 349, R03 388, R04 394로 기록했습니다. 이 한도는 반환 후 확인한 값이며 호스트가 생성을 강제로 잘랐다는 의미가 아닙니다.

공통 관리자 안내도 실제 설치·네트워크·쓰기 등을 금지했습니다. 따라서 R03의 미실행이 역할 지침만의 효과라고 분리해서 입증하거나, 실제 호스트 격리·권한 강제를 검증한 결과라고 주장할 수 없습니다. 피평가자는 독립된 주 세션이 아닌 새 하위 역할 표면을 사용했고, 사례별 단일 표본이므로 일반적 행동 신뢰성을 보증하지 않습니다.

## 독립 판정과 후속 조치

별도의 evaluator가 실제 세션 계보, 가시적 메시지, 도구 호출·반환과 고정 평가 기준을 확인했습니다. `BEH-001`은 필수 자료와 입력 한도의 충돌, `BEH-002`는 첫 두 사례의 자료 전달 잘림으로 보존했습니다. 이번 범위에서는 재시험이나 역할 지침 수정을 하지 않았습니다. 예산을 만족하는 별도 평가 설계가 필요하다면 후속 작업으로 검토해야 합니다.

행동 사례의 실패는 평가 수행의 실패를 숨기지 않고 기록한 결과입니다. 아래 저장소 회귀 시험은 이 행동 판정과 별개입니다.

## 필수 저장소 검사

영향 범위 선택 결과 **전체 `p1-regression`**이 선택됐습니다. 두 소유 경로가 모두 새 파일이므로 기존 선택기가 `new, deleted, or mode-changed file` 사유로 전체 시험을 선택했습니다. 매핑·게이트·시험 제한은 변경하지 않았습니다.

초기 묶음 계약 후보의 첫 시험은 **108개 통과, 767.051초**였습니다. 이후 아래 게시 범위 수정을 했으므로 이 통과 기록을 최종 후보의 증거로 재사용하지 않습니다. 수정된 최종 후보의 필수 회귀 시험도 **108개 통과**, 호출 전체 **779.587초**(unittest 내부 774.403초)로 완료했습니다. 전체 회귀 시험 호출은 2회이며 총 1546.638초입니다. 같은 108개 회귀 사례를 후보별로 확인한 것이며 서로 다른 216개 사례로 세지 않습니다. 피평가 사례의 실행 횟수는 여전히 각 1회, 재시도 0회입니다.

## 게시 전 계약 범위 수정

처음에는 v1의 13개 사례를 복사한 묶음에 새 네 사례를 추가했습니다. 게시 전 점검에서 이번에 실행하지 않은 기존 합성 비밀 fixture의 사본이 게시 검사의 탐지 대상임을 확인했습니다. 원래 v1은 손대지 않고, 새 파일을 R01–R04만 담는 보충 계약으로 좁혔습니다. 게시 검사 정책·허용 목록을 바꾸거나 탐지를 피하려고 문자열을 인코딩하지 않았습니다.

실제 피평가 실행에 사용한 초기 묶음의 바이트는 로컬에 보존하고 해시 `2ff6272025cb8c80257d8d5cb18662331436e8e0df911424135d0edf182beaae`로 식별했습니다. 현재 보충 계약의 해시는 `40fb11c9476244f2098d57033100ac9ef1952a95a29c8dfb71da999e6d453a40`입니다. 선택된 네 사례 객체·관리 지침·평가 기준·예산은 같고 v1은 바이트 그대로임을 비교했습니다. 따라서 실제 응답과 독립 판정은 유지하고 피평가자를 다시 실행하지 않았습니다. 원본 묶음의 불필요한 fixture 사본은 게시하지 않고 해시와 동등성 증거만 남깁니다.
