# P0 업무 흐름 적용

## 1. 기본 정보

P0 도구를 선정한 실제 작업 경로에 연결한다. 코드가 존재하는 상태에서 나아가, 작업 기록 저장·소유 파일 등록·Git 게시 과정에서 관찰을 호출하고 거버넌스·검증 담당에게 전달하는 단계다.

적용 범위는 현재 저장소의 `multi / agent-framework / development` 작업이다. 이슈는 각 작업에 지정된 정확한 값을 사용한다. 모든 셸·도구 호출을 가로채는 기능은 아니다.

## 2. 목표 및 완료 기준

- 실제 P0 호출과 관찰 기록이 자동 생성된다.
- 실행 환경이 없거나 호출이 실패한 상태를 성공으로 보고하지 않는다.
- 범위·정책·대상 파일이 바뀌면 이전 관찰을 그대로 재사용하지 않는다.
- 거버넌스 해석과 독립 검증이 정확한 기록에 연결된다.
- 정상·거부·추가 검토·실패·기존 승인 재사용 사례와 기존 회귀를 검증한다.

## 3. 결과 요약

| 구성 | 적용할 동작 | 의미의 한계 |
|---|---|---|
| 작업 기록 저장·소유 파일 등록 | 작업 소유 파일 집합에 대해 관찰 호출 | 파일 변경 실행을 승인하거나 모든 쓰기를 감시하지 않음 |
| Git 게시 직전 | 실제 생성된 커밋과 기존 게시 범위를 관찰 | 기존 승인·게시 검사를 대체하지 않음 |
| 거버넌스 담당 | 현재 기록의 정책·위험 조건을 해석해 연결 | 권한 발급·법규 인증이 아님 |
| 검증 담당 | 호출·대상·해석 근거를 확인해 연결 | 서명된 실행 증명이나 권한 인증이 아님 |

모든 관찰은 `executable=false`, `authority_verified=false`다. `allow`도 실제 실행 승인이 아니며, `deny`가 기록됐다는 사실만으로 호스트가 자동 차단한 것은 아니다.

게시 관찰은 관리 기록을 포함한 실제 커밋의 전체 변경 경로와 Git 객체 ID·모드·크기·삭제 상태를 연결한다. 작업 폴더의 현재 바이트나 Git 인덱스 표시를 커밋 내용의 증거로 사용하지 않는다. 초기 게시 관찰은 현재 설정된 HTTPS origin을 지원하며 다른 전송 방식은 명시적으로 준비되지 않은 상태로 표시한다.

## 4. 수행 내용

### 호출 환경과 선택

`.agent-work/observation.json`이 활성 범위를 선택한다. `.venv-controls`에는 고정된 의존성이 설치되며 전역 Python이나 다른 프로젝트를 변경하지 않는다. 가상환경은 Git에 올리지 않는다.

다른 체크아웃에서는 가상환경과 고정 의존성을 먼저 준비해야 한다. 환경이 없으면 명시적으로 사용 불가 상태를 반환하며 정상 작업 도중 패키지를 자동 설치하지 않는다.

설치 명령은 `python -m venv --copies .venv-controls`다. 체크아웃 밖을 가리키는 인터프리터 링크는 허용하지 않는다. 등록된 저장소도 현재 프레임워크와 동일한 실제 체크아웃이어야 한다. Python 가져오기 격리와 OS·자격증명 격리는 다른 기능이다.

### 담당자 흐름

1. 오케스트레이터가 기존 작업을 등록하고 정확한 소유 파일을 지정한다.
2. 연결된 코드가 실제 관찰을 호출하고 현재 상태를 반환한다.
3. 정책·위험 해석이 필요한 경우 거버넌스 담당이 실제 기록을 읽고 권고를 남긴다.
4. 검증 담당이 관찰·해석·현재 대상을 확인하고 별도 평가를 남긴다.
5. 변경·누락·실패·오래된 기록은 그대로 표시하고 필요한 범위만 다시 관찰·검토한다.

이미 승인된 일상 작업이나 정확히 일치하는 Git 상시 승인에 반복 승인을 요구하지 않는다. 담당자가 선언한 신원은 로컬 일관성 검사에 사용하며 인증된 신원으로 설명하지 않는다.

### 상태 확인

```powershell
python runtime/control_integration.py status --task p0-workflow-apply
```

수동으로 관찰을 갱신할 때:

```powershell
python runtime/control_integration.py observe --task p0-workflow-apply
```

이전 기록이 유효하지 않으면 원인을 확인한 뒤 `observe --task p0-workflow-apply --refresh`로 새 기록을 만든다. 이전 바이트와 제한된 해시·출처 기록을 보존하며 이전 평가를 새 기록에 옮기지 않는다.

호출기가 저장소에 설정된 관찰용 Python을 선택한다. `assess` 명령은 검토자가 작성한 지정 형식의 평가를 정확한 관찰 기록에 연결한다. 정상 운영에서는 담당 에이전트가 이 절차를 수행한다.

## 5. 산출물

- 실행 연결 코드: `runtime/control_integration.py`, `runtime/control_workflow.py`
- 실제 연결 지점: `runtime/repoctl.py`, `runtime/repo_automation.py`
- 적용 설정: `.agent-work/observation.json`
- 역할 지침: `core/orchestrator`, `core/policy-manager`, `core/evaluator`
- 영어 구현 명세: [application.en.md](application.en.md)
- 작업 기록: `.agent-work/tasks/p0-workflow-apply/`

새 기록은 기존 제출 증거를 덮어쓰지 않는다. 실제 코드 변경과 적용 증거는 작업 결과와 파일 해시 목록으로 확인한다.

관찰 요약은 체크포인트의 작업 명세·기록·한국어 보고서에도 저장한다. 실제 커밋 생성 후의 게시 관찰은 별도 로컬 기록과 반환 값으로 남기며, 이미 만들어진 커밋에 새 증거를 넣기 위해 완료 커밋을 반복 생성하지 않는다.

## 6. 검증 결과

실제 테스트 수·독립 검토 결과·현재 작업의 관찰 및 역할별 평가 기록은 최종 `result.json`에서 확인한다. 이 안내 자체를 테스트 통과 증거로 사용하지 않는다.

작업 대상 변경·오래된 기록·환경 누락·호출 실패가 명확히 표시되는지와 기존 게시 보호가 유지되는지를 확인한다. 거부·추가 검토 결과가 올바르게 처리됐는지 평가하는 것은 해당 행동을 승인하는 것과 다르다.

## 7. 미해결 사항 및 다음 조치

이번 단계의 적용 완료는 선정한 작업 경로의 관찰 호출·기록과 담당자 절차가 실제로 동작한다는 의미다. 임의의 직접 셸·Git 호출을 막는 보안 경계나 신뢰된 서명·권한 검증은 제공하지 않는다.

관찰 실패가 있어도 기존에 별도로 승인된 작업은 기존 권한·게시 규칙에 따라 처리될 수 있다. 실패를 보고하고 검토하는 절차와 코드의 강제 차단을 구분해야 한다. P1에서 제출·게시 검사와의 강제 연결을 별도로 설계하고, P2에서 실제 격리·우회 차단을 검증한다.

시간 초과·비정상 종료 뒤 잠금이 남으면 프로세스 종료와 OS PID 부재를 확인하고, 해당 작업의 정확한 잠금 파일 경로·내용을 확인한 뒤 그 파일만 제거한다. 생존 여부나 PID 재사용이 불확실하면 유지한다. 불변 관찰·평가 기록은 그대로 보존한다.
